# Wingline 阶段 0+1（验证 + MVP）实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal：** 交付 `wl up / ps / send / down` 四条命令和 `duo` 模板，能在 macOS、Linux、Windows 上通过 Orca CLI 拉起、查看、联系、关闭一个两岗位团队；同时完成阶段 0 的 5 个探针和报告。

**Architecture：** pnpm monorepo，`packages/core` 放全部逻辑（OrcaClient、规格、注册表、启动包、命令），`packages/cli` 只做参数解析与输出。所有 Orca 交互都是 `orca … --json` 子进程调用，经 `OrcaRunner` 统一解析信封、映射错误、写调用日志。命令逻辑通过依赖注入拿到 `OrcaClient` 和 `Registry`，单元测试用假实现。

**Tech Stack：** TypeScript 5、Node ≥ 22.13（`node:sqlite`）、pnpm workspaces、commander、zod、yaml、vitest、tsx、GitHub Actions。

> **2026-10-13 修订：** 任务 1–4、6–12 已按此计划实现；在 Linux 上对真实 Orca 1.4.222 验证后，下列内容已按实测改写（详见 `spikes/REPORT.md` 与 spec 7.7、2）：终端标题查找须经 `--include-visual-layouts`；`terminal send` 回执在 `result.send.*`；`--retry-request` 只接受 Orca 分配的 UUID、`terminal create` 没有该参数，本地账本键不再发给 Orca；`terminal wait` 超时是 `ok:false`/`timeout`；首期不创建 Run、不查 `worker-list`；`wl send` 增加 `--retry-request`。任务 5 的探针只在 Linux 运行过。

**Spec：** `docs/superpowers/specs/2026-10-10-wingline-design.md`（下称 spec）。实现者必须同时阅读 spec 第 2、6、7 节。

## Global Constraints

- Node 版本下限：`>=22.13`（`package.json` 的 `engines.node`）。
- 运行时依赖只有：`commander`、`zod`、`yaml`。SQLite 用内置 `node:sqlite`，禁止引入原生模块。
- 命令名：`wingline`，别名 `wl`；npm 包名 `wingline`（由 `packages/cli` 发布）。
- 数据根目录：`$WINGLINE_HOME`，缺省 `~/.wingline`（Windows 为 `%USERPROFILE%\.wingline`）；注册表 `state.db`，日志 `logs/`。
- 只经由 `orca … --json` 操作 Orca；不读写 Orca 内部文件，不调用 Orca RPC。
- 子进程一律 `spawn(file, args, { shell: false })`；唯一例外是 Windows `.cmd` 包装，经 `cmd.exe /d /s /c` 且参数用 `escapeCmdArg` 转义。
- 每个改变 Orca 状态的步骤，调用前先写本地 `requests` 账本为 `pending`，键 `<team>:<post>:<step>:<specHash 前 8 位>`（岗位前一轮生命周期已完成、或相同消息再次发送时加 `-N` 后缀）。账本键**不发给 Orca**：Orca 的 `--retry-request` 只接受它自己分配的 UUID（回执 `mutation.requestId`），`terminal create` 没有该参数。创建终端靠按标题查找保证不重复；发送类调用把 Orca 的请求 ID 记入回执，确认时由 `wl send --retry-request <id>` 带回。
- 不确定就不动手：超时、只拿到 `input_accepted`、`close.ptyKilled` 不为 true 时，标记 uncertain，绝不自动重发、重建或关闭。
- 退出码：0 成功；1 用户输入错误；2 Orca 明确报错；3 结果不确定；4 内部错误。
- 固定数值：`terminal wait` 超时 60000 ms；`--wait-submit 10`；启动包上限 12,000 字符；`wl send` 消息上限 4,000 字符；注册表回执截断 16 KB；日志消息正文截断 200 字符；日志保留 7 天。
- Orca `--json` 信封：成功 `{ id, ok: true, result, _meta }`；失败 `{ id, ok: false, error: { code, message, data? } }`，失败退出码 1。
- 用到的 Orca 结果字段（已在 Orca 1.4.222 上用真实回执核对）：
  - `terminal list --include-visual-layouts` → `result.terminals[]`（`handle`、`tabId`、`connected`、`worktreeId`；其 `title` 是 shell 窗口标题，**不是**岗位标题）与 `result.visualLayouts`（递归的布局树，标签页对象 `{ tabId, title, panes }` 的 `title` 才是 `--title` 设的自定义标题）
  - `terminal create` → `result.terminal.handle`
  - `terminal wait` → `result.wait.satisfied`；超时时回执是 `ok:false`、`error.code === 'timeout'`
  - `terminal send` → `result.send.accepted`、`result.send.prompt.stages`（含 `'input_accepted'`、`'turn_started'`）、`result.mutation.requestId`
  - `terminal close` → `result.close.ptyKilled`
  - `status` → `result.runtime.reachable`
  - `--version` → 纯文本一行版本号
- CI 矩阵：`macos-latest`、`ubuntu-latest`、`windows-latest` × Node `22.13`、`24`。

## Review Focus

1. **消息或启动包含引号、换行、`%`、`^`、`&`、中文**：经 `orca.exe` 或 POSIX 时原样送达；经 Windows `.cmd` 时，单行内容原样送达，启动包改为写文件后发送一行指引，含换行的 `wl send` 消息报输入错误并提示 → 任务 2 `escapeCmdArg` 用例 + 任务 9 启动包文件测试 + 任务 10 `send` 测试。
2. **team.yaml 路径含空格或 Windows 反斜杠**：`norms`、`brief` 能正确解析，规格哈希在三平台一致 → 任务 6 测试。
3. **Orca 没运行**（`status` 回 `runtime.reachable: false` 或错误码 `runtime_unavailable`）：退出码 2，提示 `orca open`，不调用后续命令 → 任务 3、任务 9 测试。
4. **Orca 输出不是 JSON**（版本过旧、打印了警告行、PATH 里是别的 `orca`）：退出码 4，消息里带输出前 500 字符和日志路径 → 任务 3 测试。
5. **同一团队并发执行两次 `wl up`**：不产生重复终端；第二个进程等锁或报“正在进行” → 任务 7 锁测试 + 任务 9 测试。

  - `interface RunOptions { timeoutMs?: number }`（缺省 120000）
